## 4. The status bar (the fiddly part)

The status-bar colour has to track the *effective* theme, which is not always the
device's. **This is where I found a bug during QA — see below.**

| ID | What to check | How | Expected | Who | Status | Notes |
|----|---------------|-----|----------|:---:|:------:|-------|
| B-20 | System hands control to the browser | Pick System, inspect `<meta name="theme-color">` | **Two** metas, each with a `media` attribute | 🤖 | ✅ | The browser re-evaluates these itself when the OS flips |
| B-21 | Forcing light on a dark device | OS dark, tap the sun | **One** meta, no `media`, `#FFFBF7` | 🤖 | ✅ | Without this the status bar stays plum above a cream app |
| B-22 | Forcing dark on a light device | OS light, tap the moon | **One** meta, no `media`, `#241726` | 🤖 | ✅ | |
| B-23 | Switching back restores it | Force a theme, then pick System | Back to two media-scoped metas | 🤖 | ✅ | Guarded by `lib/theme.dom.test.ts` |
| B-24 | On the installed app | Install on Android, try all three options | Status bar matches the app, no seam | 👤 | ⬜ | ⭐ **The row only your phone can answer** |

### The bug I found here

My first version replaced the media-scoped metas with a single fixed one in *every*
case, including System. That looked fine until I tested it: with System selected and
the OS on dark, the page went plum but the status bar stayed **cream**, because the
meta was pinned to whatever the theme was when you last tapped.

The fix is that JavaScript now only takes over when you have actually overridden the
device. On System the browser keeps the media-scoped pair and tracks the OS itself —
one less moving part, and no event to miss.

## What Block B built

- **`app/globals.css`** — the palette split in two. A **brand scale**
  (`habibit-400/500/600`) that is fixed and matches the icon, and **semantic roles**
  (`surface`, `card`, `ink`, `ink-soft`, `line`, `accent`, `on-accent`, four badge
  tokens) that flip between themes. Because Tailwind v4 compiles utilities to
  `var(--color-*)`, dark mode is a variable swap — **no component logic changed.**
- **`lib/theme.ts`** — preference storage, the DOM write, and the pre-paint script.
- **`lib/useTheme.ts`** — a `useSyncExternalStore` store, so no hydration mismatch.
- **`components/ui/ThemeToggle.tsx`** — a three-option radiogroup.
- **`lib/contrast.test.ts`** — parses the real stylesheet and asserts every pair.
  Also asserts the two dark-mode rules stay identical, since they are declared twice
  (one media-gated, one not) and cannot be merged.

### Deviations from the approved plan

| Plan said | Actually did | Why |
|---|---|---|
| Fix five contrast pairs | Fixed **six** | The `×` delete icon was at 2.29:1 — as bad as the placeholder, and I had missed it when scoping |
| The toggle re-applies the status bar when the OS flips | JS does not touch the status bar at all on System | Found during QA that taking over unconditionally *broke* OS tracking. Letting the browser keep its media-scoped metas is simpler and cannot miss an event |
| — | Removed `resolveTheme`, `systemPrefersDark`, `useResolvedTheme` | That status-bar fix left them with no callers. Unused exports with passing tests give false confidence |
| — | `setAttribute('media', …)` rather than `meta.media` | `media` on `<meta>` is a recent addition and is not reflected as a property everywhere — the jsdom test caught it |
